# 生命周期与扩展点设计总览

## 目标

Phase 3 只确定业务对象和业务流程的生命周期、状态转换、失败恢复、扩展点和设计模式取舍。技术框架、具体中间件、线程模型、持久化实现和 UI 框架留到 Phase 4。

本阶段继续遵守数据驱动页面的原则：

```text
日志数据
  -> 解析与索引
  -> 规则加载与校验
  -> 时延分析结果
  -> 页面投影 / CSV 投影
```

UI 和 CSV 不直接读取 TOML，不重新扫描日志，不重新计算时延。

## 核心生命周期对象

| 对象 | 生命周期重点 | 当前决策 |
| --- | --- | --- |
| 日志数据集 | 加载、解析、索引、替换、失败恢复 | 新数据集加载成功后原子替换旧数据集；失败保留旧数据集。 |
| 规则集 | 读取、校验、组装、激活、列表维护、删除、快照 | 先导入完整规则集，校验通过后进入列表；详情编辑通过选中条目完成。 |
| 分析运行 | 固化输入、执行流水线、发布结果、失败恢复 | 新分析成功后原子替换旧结果；失败保留旧结果。 |
| 分析结果 | 当前、过期、失败、不存在 | 日志或规则变化后旧结果标记为 `STALE`，可查看但不可导出。 |
| 搜索条件 | 创建、复用、编辑、删除 | 作为用户复用配置持久化。 |

## 第一版持久化边界

只持久化用户会复用的配置，不持久化可重建的大体量运行结果。

需要持久化：

- 业务规则 TOML 文件。
- 已保存搜索条件。
- 最近打开的日志文件路径。
- UI 偏好设置，例如列宽、选中场景、默认时间范围。

不需要持久化：

- 解析后的日志索引。
- 请求识别结果。
- 时延分析结果。
- 统计结果。

这些结果都由日志数据集和规则集重新生成，避免缓存失效和版本不一致问题。

## 本地索引边界

第一版使用本地内存索引，不引入外部搜索中间件。

```text
ParsedLogDataset
  -> LogIndex
     -> 基础索引：时间、应用、级别、原始行号
     -> 匹配结果索引：log_matcher 命中与日志引用
```

基础索引用于时间范围筛选、上下文查看、请求边界定位。匹配结果索引用于时延分析、关键日志展示和 CSV 导出。

日志搜索和时延分析共用同一份 `LogIndex`，避免重复扫描日志。

## 异步任务边界

日志加载、规则校验和时延分析可以异步执行，但第一版不引入任务队列中间件。

- 同一时间只允许一个加载任务。
- 同一时间只允许一个分析任务。
- 重复点击执行按钮时，应用层直接拒绝或禁用入口。
- 查询、查看、筛选读取最近一次成功的数据快照。
- 任务失败不破坏旧数据、旧规则或旧分析结果。
- 进度只通过 `ProgressListener` 通知 UI，监听器失败不能中断主流程。

## 结果投影边界

时延分析完成后只产出稳定的 `LatencyAnalysisResult`，展示和导出各自生成投影：

```text
LatencyAnalysisResult + EffectiveRuleCatalog
  -> LatencyAnalysisViewModel
  -> LatencyAnalysisCsvModel
```

- 页面样式变化只影响 `LatencyAnalysisViewModel` 和 UI。
- CSV 格式变化只影响 `LatencyAnalysisCsvModel` 和导出适配器。
- 时延分析核心不关心 UI 坐标、颜色、表格列宽或 CSV 编码。

## 阶段结论

第一版重点是把生命周期和数据边界定稳，不做外部插件框架，不引入外部搜索服务，不持久化分析缓存。核心扩展通过内部接口、流水线步骤、策略、职责链、拦截器和监听器完成。
