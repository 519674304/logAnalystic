# 当前实现差距与整改计划

## 目的与边界

本文把当前代码评审和时延分析链路审查中已经确认的问题转化为可执行的整改顺序，并记录已明确的范围边界，避免后续实现重新解释已作出的决定。

本文不批准新的业务语义，也不授权直接修改代码。涉及业务语义的未决项必须先更新需求、职责设计、基线和验收样例，再进入实现。

## 已确认的目标流程

时延分析的输入和处理顺序固定为：

```text
日志
  -> 时间范围过滤
  -> 过滤有效的请求开始日志
  -> matcher 匹配请求内日志
  -> 过滤有效 matcher
  -> 按 stage 组织边界
  -> 形成有效请求链
  -> 输出分析结果与展示投影
```

含义如下：

- 日志目录是原始输入；前端不应先读完整日志再传给分析服务。
- 时间范围必须作为分析输入传入服务端，由日志读取层过滤。
- 请求开始日志、matcher 命中和 stage 边界都在经过范围过滤后的请求内日志上判定。
- 无法形成有效请求链时，应返回明确的空结果或无效原因，不能替换为演示结果。

## 本期不作为问题的事项

下列行为已由当前讨论明确，不应被后续整改误报为缺陷：

| 事项 | 当前决定 |
| --- | --- |
| flow 级 stage 的展示行为 | 现状是设计预期。 |
| matcher 的 `enabled` 级联 | 不做级联判断；只要 stage 引用了 matcher，就参与该 stage 的匹配。 |
| 请求总耗时的严格聚合边界 | 当前不是优先问题，后续再按需要细化。 |
| 同一请求多个结果分支同时命中 | 发生概率低，当前不以此阻塞整改。 |
| 区间统计 | 后续单独处理，不纳入本计划。 |

这些边界不改变已批准需求中的其他规则；若以后要改变，先走需求变更。

## 已确认的功能差距

### GAP-LATENCY-001：时间范围没有进入实际时延分析

**现状。** `runLatencyAnalysis` 调用 `analyzeLatencyStream` 时只传递日志目录和规则投影；请求体虽支持 `start_time` / `end_time`，但前端没有传入。服务端日志源只有收到范围时才过滤，因此当前时延分析会扫描所选目录的全部日志。

**影响。** 用户在界面上选择的时间范围不能约束请求识别和 stage 匹配，结果可能包含范围外请求，也会增加无谓扫描。

**处理。**

1. 将时间范围作为 `analyzeLatencyStream` 的显式输入，并映射到 HTTP 请求的 `start_time` / `end_time`。
2. 从时延分析入口传递用户已确认的范围；保持日志读取和过滤在服务端完成。
3. 为范围内、范围外、边界时间戳三类输入建立端到端基线，断言范围外请求和阶段样本不会进入结果。

**完成证据。** API 请求契约测试、服务端范围过滤测试和一份端到端冒烟基线同时通过。

### GAP-LATENCY-002：真实空结果会回退为演示数据

**现状。** 前端把 `app-state.ts` 中的 `latencyResult` 转为 `sampleLatencyViewModel`，当没有真实分析结果或没有有效 stage 时，视图模型构建函数会返回该样例。

**影响。** 用户可能把演示请求和阶段误认为本次运行结果；空结果、规则无效和分析失败也无法被区分。

**处理。**

1. 明确定义分析结果状态：未运行、运行中、成功有数据、成功无数据、规则无效、失败。
2. 真实运行路径只能消费本次分析返回的数据；样例仅可用于独立预览或开发 fixture，不能作为运行回退。
3. 在结果为空、stage 无效和请求链无效时，展示对应原因与下一步，而不是渲染样例泳道。

**完成证据。** 用例分别覆盖上述状态，且“无结果”断言页面不包含任何样例请求或样例阶段。

### GAP-LATENCY-003：结束日志早于开始日志时被静默计算为 0 ms

**现状。** 分析器分别从请求内日志中挑选 start 和 end 命中，再将 `end - start` 截断为不小于 0。因此选择到开始之前的结束日志时，会产出看似有效的 0 ms 阶段。

**影响。** 日志乱序、重复结束事件或不完整请求会被掩盖，统计结果中混入错误样本。

**处理。**

1. 在已选定阶段开始边界之后再寻找可用的结束边界。
2. 未找到后续结束边界时标记阶段或请求链不完整，不生成 0 ms 的伪样本。
3. 增加“结束早于开始”“重复结束”“缺少结束”基线，明确每种输入的结果和原因。

**完成证据。** 分析器单元测试与基线测试证明错误时序不会产生 0 ms 有效阶段。

### GAP-LATENCY-004：场景不影响请求开始边界

**已定语义。** 场景不会影响 flow 层级。流程级 `order=1` 请求开始 stage 及其引用 matcher 始终从完整规则集中投影；场景只过滤请求内的普通 matcher、stage、体检规则与展示内容。

**实现要求。** 分析入口必须分别传入场景有效规则和完整规则：前者生成 matcher/stage 投影，后者只生成 `requestStarts`。同一日志在不同场景下的请求数量和开始边界必须一致。

**完成证据。** `check-effective-rule-resolver.ts` 以一个对当前场景不可见的 flow 开始 stage 验证：仍使用完整规则集的开始 matcher 形成请求边界。

### GAP-TEST-001：UI 契约检查已失效且不能证明行为

**现状。** `npm run test:ui-contract` 仍检查旧文案“起点步骤 / 终点步骤”，当前界面已经使用“起点 / 终点”，导致检查失败。该脚本主要是源码子串断言，无法覆盖实际的请求、状态和结果行为。

**影响。** 当前 CI 既有误报，也不能阻止时间范围漏传、样例回退或空态错误等业务回归。

**处理。**

1. 先把过期文案断言改为现行 UI 契约，恢复基础检查可信度。
2. 将关键业务行为移至合适层级测试：API client 请求体、视图模型状态、分析器边界和端到端 fixture。
3. 文案存在性检查只保留为辅助校验，不能作为业务验收证据。

**完成证据。** UI 契约检查恢复通过，并且关键时延样例有可执行输入输出基线。

## 结构性架构债

以下问题来自 [代码架构评审](../code-review-findings.md)。它们不替代上述功能整改；应在功能语义稳定后按小批次重构。

| 编号 | 问题 | 处理方向 | 验证方式 |
| --- | --- | --- | --- |
| ARCH-001 | `App.tsx` 承担状态、规则投影、导出、持久化和平台兜底；投影逻辑重复 | 先抽共享的 `EffectiveRuleResolver` 和导出/持久化模块，再按 feature 拆分容器；运行路径移除样例和废弃 Tauri 兜底 | 共享投影单测、既有 UI 冒烟、无废弃路径引用检查 |
| ARCH-002 | application 层直接构造具体日志源和 store | 用 port 注入依赖，具体 infrastructure 只在组合根装配 | fake port 的 application 测试、依赖方向检查、`cargo test --workspace` |
| ARCH-003 | `main.rs` 混合 DTO、映射、handler、路由、观测和组合根 | 按 DTO / mapping / handlers / router / diagnostics 拆分；消除重复映射 | handler 与 mapping 测试、路由冒烟、`cargo check --workspace` |

重构不应与未决业务语义混在同一个提交中。每一项先保持外部契约和基线不变，再改变内部结构。

## 建议实施顺序与检查点

| 阶段 | 目标 | 开始前检查 | 完成条件 |
| --- | --- | --- | --- |
| 0 | 定义场景与请求开始边界语义 | 明确 GAP-LATENCY-004 的业务决定 | 需求、职责和基线已同步；未实施代码猜测 |
| 1 | 让时间范围真正约束分析 | 审核 API 输入、服务端范围过滤和目标流程 | GAP-LATENCY-001 的三层测试与基线通过 |
| 2 | 消除样例回退并明确运行状态 | 定义所有结果状态及其 UI 文案 | GAP-LATENCY-002 的状态测试通过，真实空结果可见 |
| 3 | 修正阶段边界配对 | 确认“开始后找结束”的不变量 | GAP-LATENCY-003 的异常时序基线通过 |

| 5 | 清理结构性架构债 | 前四阶段的外部契约稳定 | 分项完成 ARCH-001～003，并完成架构复审 |

每个阶段都按“文档契约 → 实现映射 → 小的端到端切片 → 证据”闭环执行。若实现中发现需求、基线或职责边界不一致，应停止扩展实现，先记录偏差并重新确认，而不是在代码中静默修正语义。

## 变更与验收清单

每次整改提交至少记录：

- 关联的 GAP 或 ARCH 编号；
- 本次不变量和不处理的范围；
- 改动前后的输入输出样例；
- 执行的定向测试与其结果；
- 若涉及流程语义，已更新的需求、职责、基线和 UI 契约。

完成本文全部阶段的判定是：时延分析主链路按本文流程执行；真实结果不再被样例覆盖；错误时序不产生有效伪样本；关键行为有可执行证据；并且结构性重构没有破坏已批准外部契约。
