# 时延分析需求

> 因「规则集结构收敛（3 层）」而修订：取消 `role="start"` / `role="end"` 边界 stage；flow 中只有 stage，stage 的 matcher 自带 start/end；stage 以 owner 区分进程级（`process_id`）与流程级（`flow_id`），流程级 stage 是自定义起止段（可概括一个或多个进程、可跨应用，串起完整流程），常按 `result` 拆结果分支；同 `order` 的多个结果分支在定义上都存在，执行时同一 `order` 只命中一个。原 REQ-LATENCY-003/004/005/007/008/009/011/012/013/018/019/020 语义按新模型重写。

## 需求列表

- REQ-LATENCY-001: 系统根据规则集中明确配置的阶段计算时延，不自行推断阶段。
- REQ-LATENCY-002: 每个时延阶段至少包含阶段名称、开始日志规则、结束日志规则。开始与结束日志规则都可配多个 matcher（`start_matcher_ids` / `end_matcher_ids`），**按数组顺序优先**（首个命中的决定起止），减少端侧日志丢失导致的阶段丢失。
- REQ-LATENCY-003: 阶段按 owner 区分进程级与流程级：进程级阶段属于进程（`process_id`），表达进程内部处理；流程级阶段属于流程（`flow_id`），表达自定义起止的流程段，可概括一个或多个进程、可跨应用，串起完整流程（常见写法为各进程整体聚合与跨应用 RPC）。
- REQ-LATENCY-004: 进程级阶段通过 `process_id` 指定所属进程，其所有 matcher 与父进程同应用。
- REQ-LATENCY-005: 流程级聚合阶段（常见写法）表达一个进程或多个进程整体的跨度，按 `result` 拆分为多个结果分支；同 `order` 的多个结果分支在定义上都存在，执行时同一 `order` 只命中一个。
- REQ-LATENCY-006: 请求总耗时按聚合阶段的跨度（开始边界到命中结果分支的结束边界）计算；无结束日志时，请求可分析范围截止到下一次开始日志之前的最后一条请求日志。
- REQ-LATENCY-007: 进程级阶段用于表达某个进程内从开始到完成的耗时。
- REQ-LATENCY-008: 跨应用 RPC 阶段（流程级）表达一个应用完成到另一个应用开始之间的耗时，该阶段不属于任何单一应用。
- REQ-LATENCY-009: 进程内部更细粒度的步骤通过多个进程级阶段表达。
- REQ-LATENCY-010: 同一阶段规则在一次请求中重复匹配时，使用第一次匹配。
- REQ-LATENCY-011: 流程可有多个结果分支，命中不同 `result` 分支（同 `order`）即判定不同结果；同 `order` 只命中一个。
- REQ-LATENCY-012: 结果分支由聚合 stage 的结束匹配器识别；同 `order` 的多个结果分支都命中时，取时间最先命中者决定结果，其余记 Issue。
- REQ-LATENCY-013: 不同结果对应不同的 `result` 值，互不相同。
- REQ-LATENCY-014: 系统提供请求总耗时、阶段耗时、同类请求统计、慢阶段和异常请求数量。
- REQ-LATENCY-015: 用户执行时延分析前选择一个规则集定义的分析场景。
- REQ-LATENCY-016: 系统只匹配和计算 `enabled=true` 且当前场景包含在 `applicable_scenario_ids` 中的日志匹配器与阶段。
- REQ-LATENCY-017: 分析场景只控制普通关键日志、阶段计算和导出内容，不改变已经识别的请求数量、开始边界或结果。
- REQ-LATENCY-018: 跨子进程并行由进程级阶段（带 `sub_process_ids`）表达：主进程完成触发后，在同一次 req 内分别匹配组内各子进程日志；子进程可以并行且不要求按配置顺序完成。
- REQ-LATENCY-019: 跨子进程并行阶段在主进程汇总日志命中时完成；其耗时为触发点到汇总点的时间差，汇总日志之后主进程可以继续后续阶段。
- REQ-LATENCY-020: 请求开始由流程级聚合阶段（`order=1`）的开始匹配器命中标记并创建一次请求；请求结果由命中的 `result` 分支判定。
- REQ-LATENCY-021: 拦截过滤——`kind="intercept"` 的拦截 stage 用 `end_matcher_ids`（数组）列出全部拦截结束事件，任一命中即判定该请求被拦截；被拦截请求整个丢弃，不生成任何阶段样本、不进统计，也不单独计数。owner 可为 flow 级或进程级，命中一律丢整个请求。

## 阶段示例

对于从 A 应用到 B 应用的请求，可以配置为：

```text
完整请求 A->B 整体（结果分支）   = 流程级聚合阶段（flow_id，result=SUCCESS/ERROR，同 order 只命中一个）
请求开始 -> A 进程完成           = A 进程的进程级阶段（process_id = A）
A 进程完成 -> B 进程开始         = 跨应用 RPC 流程级阶段（flow_id，起止落在不同应用）
B 进程开始 -> B 进程完成         = B 进程的进程级阶段（process_id = B）
```

对于 `a日志 -> b日志 -> c日志` 的场景：

```text
a日志 -> b日志 = b阶段
b日志 -> c日志 = c阶段
```

阶段命名由规则集定义。颜色、布局和图表样式属于展示需求，不影响时延计算规则。

## 主流程

1. 用户选择分析场景和某一次请求。
2. 系统读取该请求所属业务流程、命中的结果分支及当前场景下的有效规则。
3. 系统按规则集中的阶段匹配阶段边界日志。
4. 系统计算每个阶段的开始时间、结束时间和耗时。
5. 系统汇总请求总耗时和各类阶段耗时。
6. 存在跨子进程并行阶段时，系统分别计算子进程阶段，并以主进程汇总日志计算该阶段总等待时延。
7. 系统按命中的聚合阶段 `result` 分支判定请求结果。
8. 系统生成与展示无关的时延分析结果。
9. 展示层消费分析结果，绘制阶段视图和统计摘要。

## 验收标准

- 给定明确阶段规则，系统可以计算阶段耗时。
- 阶段结果包含阶段名称、起止日志、耗时、所属进程或所属流程。
- 跨应用 RPC 耗时可以在图上独立展示。
- 有多结果分支的请求按命中的 `result` 分支判定结果，未命中的分支不展开。
- 同类请求统计不替代单次请求明细，用户选择的请求始终是主视图。
