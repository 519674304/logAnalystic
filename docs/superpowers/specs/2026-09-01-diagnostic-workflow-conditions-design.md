# 诊断工作流（健康检查）· 完整设计

> 从业务讲起，用「唤不醒」的三个场景把「日志 → 搜索 → 命中/不命中 → 结论 → 界面」从头走到尾，说清楚核心模型：**一个搜索原语 × 三种下界 + stage 配对**。
> 诊断工作流与「时延分析」**解耦，单独处理**——它只做「在某个时间范围内找 marker 是否命中」，不复刻时延分析的 request 拆分 / 去重逻辑。

## 一、业务：要解决什么问题

用户对语音设备说话，设备偶尔「唤不醒」——说了唤醒词，设备没反应。开发/运维要能回答：**这一次为什么唤不醒？**

排查唤不醒通常要确认三件事：

1. 唤醒开关有没有打开？
2. 设备是不是还在收音（没退出收音态）？
3. 到底有没有收到唤醒请求？

这三件事分别对应三种**不同的搜索范围**——这就是本设计要统一的点。

## 二、核心模型：一个搜索原语 × 三种下界

诊断的底层动作只有一个：**在某个时间范围内，找某个 marker（matcher 或 stage 的 start/end）是否命中**。结果只有「命中 / 不命中」。

所有搜索都从**时间窗终点 `t1` 往回找**，差别只在**下界**：

| 模式 | 搜索范围 | 下界 | 什么时候用 |
| --- | --- | --- | --- |
| 仅时间窗 | `[t0, t1]` | `t0` | 只关心用户选的时间窗内有没有 |
| 有界回溯 | `[t0 − W, t1]` | `t0 − W` | 时间窗 + 往前 W；W 相对 t0，建规则时配 |
| 无界回溯 | `(−∞, t1]` | `−∞` | 不受时间窗限制，一直往前找到为止 |

- `t0` / `t1`：用户选的搜索时间窗起止。
- `W`：回溯窗口（如 10 分钟），**建规则时配置**，不是全局。

### stage = 一对 marker，命中后配对

stage 由 `start` / `end` 两个 marker 定义。在选定下界范围内搜完命中后，**配对**出三种状态：

| 状态 | 含义 |
| --- | --- |
| `Closed` | start 命中 + end 命中（完整走过一段） |
| `Unclosed` | start 命中 + end 未命中（开始了没结束，还在进行） |
| `Missing` | start 未命中（根本没进这个阶段） |

配对是「重组」那一步，不属于搜索本身——搜索只负责给出 start/end 各自命中与否（和命中时间）。

## 三、三个唤不醒场景（规则示例）

把三个排查点各写成一条规则，本质都是「一个 marker 命中与否 + 一个下界」：

### 场景 1：唤醒开关没打开 —— 无界回溯

开关是个状态，开和关可能在**很久以前**（早于时间窗）。只搜时间窗内会漏判，所以用**无界回溯**。

```
规则「开关未打开」:
  搜索 = 找 matcher「唤醒开关开启」，下界 = −∞（无界回溯）
  命中   → 开关开着（不报）
  不命中 → 结论「唤醒开关未打开，导致唤不醒」
```

### 场景 2：设备在收音 —— 有界回溯

收音可能从时间窗之前就开始了（用户 t0 之前开始收音、一直没收完），导致 t0~t1 内唤不醒。所以搜「时间窗 + 往前 W」。

```
时间窗 t0=10:00, t1=10:05, W=10min

日志：
09:50:00.000  audio init      ← t0 之前 10 分钟，收音开始
10:03:00.000  wake attempt    ← 时间窗内，唤醒尝试（没成功）
（没有 audio ready）

搜索 [t0 − W, t1] = [09:50, 10:05] 内的 stage「收音」：
  start「audio init」命中 @ 09:50
  end「audio ready」未命中
  配对 → Unclosed → 结论「设备正在收音，导致唤不醒」
```

### 场景 3：没收到唤醒请求 —— 仅时间窗

唤醒请求只可能在用户选的时间窗内出现，直接搜时间窗即可。

```
规则「未收到唤醒请求」:
  搜索 = 找 matcher「唤醒请求」，下界 = t0（仅时间窗）
  不命中 → 结论「未收到唤醒请求，导致唤不醒」
```

## 四、数据结构怎么串

一次诊断：**输入（规则 + 日志 + 时间窗）→ 搜索 → 命中 → 配对 → 结论**。

**① 规则**（用户配的，存成 JSON；字段名示意，后定稿）

```json
{
  "name": "收音中",
  "conclusion": "设备正在收音，导致唤不醒",
  "target": { "kind": "stage", "stageId": "audio" },
  "range": { "type": "boundedBacktrack", "windowMs": 600000 },
  "when": "unclosed"
}
```

- `target`：搜 matcher（marker id）还是 stage（stage id）。
- `range`：三种下界之一（`window` / `boundedBacktrack` / `unbounded`；`boundedBacktrack` 带 `windowMs`）。
- `when`：触发结论的结果条件——matcher 是 `hit` / `miss`，stage 是 `closed` / `unclosed` / `missing`。

**② 命中**（搜索的原始输出，带时间戳）

```json
[
  { "marker": "audio.init", "hit": true, "timestamp": "09:50:00.000" },
  { "marker": "audio.ready", "hit": false, "timestamp": null }
]
```

**③ 结论**（配对 + 判定后）

```json
{
  "ruleName": "收音中",
  "conclusion": "设备正在收音，导致唤不醒",
  "evidence": "收音开始于 09:50:00.000，未结束"
}
```

一句话串起来：**规则（搜什么 + 搜多远 + 什么结果触发）+ 日志 + 时间窗 →（搜索）→ 命中；命中 →（stage 配对）→ 状态；状态 vs `when` →（判定）→ 结论。**

## 五、数据怎么给用户展示

- **命中列表**：每条规则一行，标出「命中 / 不命中」和结论。
- **证据回放**（点开详情）：把命中的那几条日志高亮，标出搜索命中的 marker 和时间。

## 六、已定 / 待定

**已定：**

- 诊断与「时延分析」解耦，单独做 marker 搜索。
- 搜索原语：找 marker，命中 / 不命中；都从 `t1` 往回，三种下界（`t0` / `t0 − W` / `−∞`）。
- `W` 相对 `t0`，建规则时配置，非全局。
- stage = start/end 配对成 `Closed` / `Unclosed` / `Missing`。

**待定（需要拍板）：**

1. 一条规则是否可以组合多个搜索（`all` / `any` / `not`）？—— 倾向 v1 先做单搜索，组合后置。
2. 结论话术是否带时距（如「收音开始于 10 分钟前」）？—— 倾向带，命中里有时间戳就能算出来。
3. 命中多条规则时，界面并列展示还是按优先级只取一条？—— 倾向并列展示。
